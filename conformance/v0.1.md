# ZeroLocal v0.1 Conformance Checklist

This checklist distinguishes static repository evidence from live operational evidence.

## Protocol / Core Skill

- [ ] `SPECIFICATION.md` declares Skills as the current delivery form and Plugin as stabilization-gated.
- [ ] Lifecycle states exist: BOOTSTRAP, IMPLEMENT, VERIFY, PROVISION, DEPLOY, OBSERVE, REPAIR/ITERATE, CHECKPOINT.
- [ ] Seven contract families exist: Lifecycle, Repository, RPM, CI, Deployment, Trust Boundary, Provider Adapter.
- [ ] Provider hooks exist: detect, capabilities, credentials, scaffold, validate, provision, migrate, deploy, endpoint, verify, recover.
- [ ] Core Skill implements Initialize, Plan, Implement, Verify, Deliver, Observe, Checkpoint.
- [ ] Core Skill does not require a human local checkout/toolchain/CLI.
- [ ] Core Skill prohibits secret values in chat and RPM.
- [ ] Core Skill distinguishes implemented, verified, deployed, observed, and trust-boundary-blocked states.

## Cloudflare Provider Skill

- [ ] Cloudflare behavior is isolated from Core.
- [ ] Provider Skill checks current Cloudflare guidance before authoring/reviewing provider configuration.
- [ ] `CLOUDFLARE_API_TOKEN` and `CLOUDFLARE_ACCOUNT_ID` are treated as protected-store values, never chat inputs.
- [ ] Untrusted validation has no production authority.
- [ ] Delivery accepts/deploys an immutable validated SHA.
- [ ] Production operations are serialized when state-sensitive.
- [ ] Endpoint discovery uses provider/tool evidence rather than hostname assumptions.
- [ ] Production verification is externally observable.
- [ ] Recovery returns repository repair versus precise human trust-boundary action.

## Cloudflare executable reference

Static evidence expected in `iorLab/zerolocal-cloudflare-starter`:

- [ ] `ZEROLOCAL.yaml` declares provider capabilities, credentials, workflow paths, revision source, verification path, and trust boundaries.
- [ ] `.chatgpt/project-memory.yaml` and referenced RPM files exist.
- [ ] CI runs on PRs and `main` pushes without production credentials.
- [ ] Automatic Deploy is gated on successful CI from a trusted `main` push.
- [ ] Deploy checks out the exact tested SHA.
- [ ] Manual recovery takes an explicit full SHA and validates it before deploy.
- [ ] Production concurrency is serialized.
- [ ] Deployment URL/target is discovered from provider output.
- [ ] `/health` or equivalent is checked after deployment.

Live evidence, when protected provider authorization is available:

- [ ] CI passes for the released SHA.
- [ ] Deploy runs for the same SHA.
- [ ] Provider reports a deployment target.
- [ ] Health/readiness verification passes against that target.

Live provider credentials are not required for static Skill v0.1 implementation completeness. Their absence must be represented as an explicit trust boundary, not hidden as a code blocker.

## Skill v0.1 gate

Skill v0.1 is implementation-complete when all static checklist items pass and the reference CI validates its repository-owned code/configuration. Clean-room multi-project validation is the next phase and remains mandatory before Plugin work.
