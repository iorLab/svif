## Consumer implementation pressure

The existing Svif `AgnirFilesystemContinuityProvider` on `main` hard-coded Agnir Core/profile `0.1`. The validation therefore extends the real Svif provider adapter rather than merely editing manifests.

The candidate adapter:

- preserves support for Core/profile `0.1`;
- recognizes Core/profile `0.2` as a separate supported compatibility line;
- requires `continuity.lineage` on Core `0.2`;
- keeps logical lineage identity distinct from VCS selector binding;
- optionally constrains expected Core/profile from the Svif binding;
- fails explicit selected-selector binding absence/mismatch rather than guessing;
- records the resolved Agnir lineage in Svif runtime checkpoint evidence;
- keeps the generic Svif Orchestrator interface unchanged.

Focused tests add Core `0.2` discovery, binding mismatch/absence, compatibility mismatch, lineage requirement, and lineage-preserving checkpoint coverage while retaining the existing Core `0.1` cases.

## Acceptance sequence still required

This initial branch migration is only the first stage. Real-consumer validation is not complete until:

1. Svif product CI passes on the migrated branch;
2. fresh selected-lineage load/checkpoint succeeds;
3. a second temporary branch is explicitly forked into a different logical lineage with the same Project identity;
4. source and target lineages diverge and checkpoint independently;
5. staged integration leaves the target ref unchanged while unreconciled;
6. target continuity is reconciled before target publication;
7. integrated target + source both fresh-resume coherently;
8. final evidence is fed back into Agnir Core `0.2` release readiness.

No success claim for Core `0.2` real-Project validation should be made before that sequence is observed.
