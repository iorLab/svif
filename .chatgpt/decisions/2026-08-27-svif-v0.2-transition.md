# Svif v0.2 Transition Decisions — 2026-08-27

**Status:** Active architecture decisions during the Svif transition.  
**Historical consolidated decisions:** `.chatgpt/decisions.md`

This record captures decisions made after the 2026-08-27 17:58 +08:00 full checkpoint without rewriting ZeroLocal predecessor decision history.

## Svif identity and predecessor evidence

- **Svif** is the new project/protocol identity; ZeroLocal and ANRD remain predecessor identities.
- ZeroLocal v0.1 specification, `ZL-*` contracts, Skills, Cloudflare reference, and clean-room validation remain historical evidence.
- Existing ZeroLocal conformance MUST NOT be silently relabeled as Svif conformance.

## Core definition

Svif is an execution-environment-independent Project operation protocol.

The stable conceptual unit is the **Project**. Executors and execution environments may change without owning Project continuity.

Svif Core MUST NOT require ChatGPT, GitHub, Git, a particular AI agent, conversational state, remote-only execution, a human-local-checkout prohibition, Skill packaging, or Cloudflare.

## Neutral roles and surfaces

- **Principal** owns/provides intent, policy, authorization, approval, or risk acceptance.
- **Executor** performs Project operations and may be human, AI, CLI, IDE, automation, CI, service, or composed system.
- **Execution Environment** is the replaceable surface in which execution occurs.
- **Capability Adapter** connects Svif to concrete workspace, SCM, verification, delivery, provider, observation, authority, or execution-surface capabilities.

No Execution Environment becomes authoritative merely because work occurred there.

## Agnir dependency

- Svif depends normatively on a compatible **Agnir Core protocol version**.
- Svif does not require a particular Agnir implementation/backend/adapter.
- Current draft dependency target is **Agnir Core 0.1**; exact release compatibility remains unfrozen.
- Svif CHECKPOINT delegates durable persistence/discovery/resumability semantics to Agnir rather than defining a second Project Memory protocol.

## Generalized lifecycle

The target lifecycle is:

`DISCOVER -> PLAN -> CHANGE -> VERIFY -> DELIVER -> OBSERVE -> CHECKPOINT`

with `REPAIR` returning to the earliest violated invariant.

`DELIVER` is skippable when no external actuation is required. Software delivery may expand it into preparation/provisioning, migration, and deploy/publish substates.

Whether `PLAN` must always be explicit or may be implicit for trivial operations remains an open normative detail; planning semantics remain required.

## Candidate provenance and evidence

- Git SHA is no longer the only Core candidate identity.
- Svif Core uses **stable candidate provenance**: material change, verification, delivery, and observation evidence must refer to a stable/unambiguous candidate or target identity appropriate to the Project.
- Immutable full Git SHA remains a strong Software Delivery + SCM realization.
- Evidence-driven lifecycle transitions remain Core.
- Verification authority and protected delivery authority remain separable.
- Externally claimed effects require observation; successful actuation alone is insufficient.

## Capability Adapter contract

Capability Adapters declare portable semantics for:

- adapter identity/kind;
- supported capabilities;
- authority and credential references without secret values;
- evidence and candidate/result/target identity;
- failure mapping;
- retry/idempotency behavior;
- observation behavior;
- composition/provenance across adapter boundaries.

Initial adapter kinds are `workspace`, `scm`, `verification`, `delivery`, `provider`, `observation`, `authority`, and `execution_surface`.

Provider-specific hooks from ZeroLocal map into this generic adapter model rather than remaining a ChatGPT Provider Skill contract.

## Software Delivery Profile

The strong ZeroLocal software-delivery invariants move into a separate Svif Software Delivery Profile when they are not universal Core semantics.

The draft profile preserves:

- stable/immutable candidate identity;
- verification attribution;
- exact verified-candidate delivery;
- protected delivery authority separation;
- provider preparation/provisioning and migration semantics;
- state-sensitive concurrency coordination;
- protected secret handling through authorized stores/channels;
- observable production/external success;
- provider isolation;
- evidence-based repair.

Remote CI, Git repositories, branch/PR mechanics, ChatGPT Skills, and Cloudflare are implementations/profiles/adapters rather than generic Core requirements.

## Trust boundaries and secrets

Secret values must stay inside authorized protected channels/stores. Svif Core MUST NOT require secret values to be transmitted through an unprotected conversational or execution surface.

Account ownership, billing, domain ownership, external consent, destructive operations, protected credentials, and production approval may remain explicit Principal trust boundaries and must not be misreported as ordinary Project defects.

## Conformance migration

- New Svif conformance identifiers/tests should be created rather than renaming `ZL-*` identifiers in place.
- Conformance should separate Svif Core, Agnir continuity, Capability Adapter, Software Delivery Profile, and provider-specific evidence.
- Future Svif conformance must include fresh-Executor Agnir cold-start recovery and at least one materially different execution/storage arrangement from ChatGPT + GitHub + Cloudflare.
- Validation Project #2 (`mattamior/cloud-mail`) remains paused until these boundaries are concrete enough to test.
